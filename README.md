# Цифровой навигатор и конструктор маршрутов выходного дня в мессенджере MAX

## Назначение

Решение отвечает на вопрос «куда выйти сегодня в своём городе, если есть два часа и тысяча рублей».
Гость выбирает город, занятие, длительность и бюджет — получает пеший маршрут из реальных мест с
таймингами, линией переходов по тротуарам и справкой по каждой точке, и проходит его по шагам.

Три составляющих: бот в мессенджере **MAX** (приветствие, меню команд, кнопка запуска Mini App),
HTTP **API** (каталог мест, генератор маршрутов, справки, сохранение прогулок, аналитика пилота) и
**Mini App** (React: онбординг → настройки → маршрут на карте → навигация). Ядро — планировщик:
он собирает маршрут под 85 % заказанного времени, оставляя 15 % резерва, укладывается в бюджет денег
и не ставит точки дальше 2,5 км друг от друга.

## Основной пользовательский сценарий

1. Гость пишет боту в MAX (или нажимает «Старт») — получает приветствие и кнопку «🧭 Открыть навигатор».
2. Mini App открывается на экране онбординга; гость переходит к настройкам прогулки.
3. Выбор города (список приходит из `GET /api/v1/cities`), затем чипов «Чем хочешь заняться?»
   (`GET /api/v1/chips?city=`) — счётчик мест на чипе и список карточек считают по одному предикату.
4. Выбор длительности (1–4 часа), бюджета и точки старта (поиск по каталогу, `GET /api/v1/places?q=`).
5. `POST /api/v1/routes/generate` возвращает остановки с временем визита, минутами перехода,
   реальными метрами пешком и линией `geometry_from_prev` для карты.
6. Экран маршрута рисует MapLibre: маркеры по порядку, пунктиром — переходы, которые роутер не измерил.
7. «Начать прогулку» открывает навигацию: «Я на месте» → карточка места со справкой
   (`GET /api/v1/places/{id}/guide`) и соседними точками, «Далее» → следующая остановка.
8. «Завершить прогулку» подводит итог: пройдено метров и затрачено времени против плана.
9. Маршрут можно сохранить (`POST /api/v1/routes`) — он переживёт перезапуск процесса и вернётся
   в `GET /api/v1/routes`.

## Архитектура

```text
core/config.py        pydantic-settings: валидация .env, нормализация DATABASE_URL
bot/models.py         Pydantic-схемы MAX: Update/Message/Keyboard/SendMessagePayload
bot/client.py         httpx.AsyncClient: единый пул, ретраи, rate-limit 2 msg/sec на диалог
bot/keyboards.py      билдеры inline_keyboard (open_app / link / callback / message)
bot/dispatcher.py     роутинг по update_type и командам + дедупликация событий + upsert пользователя
bot/handlers/start.py приветствие, фолбэк на любой текст, ответы на callback
server/database.py    AsyncEngine + aiosqlite, PRAGMA WAL/synchronous/foreign_keys, модели User и SavedRoute
server/schemas.py     публичные контракты: Place / RouteRequest / RouteResponse / SaveRouteRequest + описания для OpenAPI
server/catalog.py     загрузка data/places.json (кэш), нестрогое сравнение города, список категорий и чипов
server/guides.py      загрузка data/place_guides.json (кэш) и расчёт соседних точек тем же шагом, что и маршрутизатор
server/routing.py     сборка маршрута: лучевой поиск самого плотного набора точек под 85 % бюджета
                      времени (остальное — резерв) и под бюджет денег, не ближе 150 м друг к другу, затем
                      2-opt порядок переходов и вставка того, что влезло в образовавшиеся окна; если
                      передан `start`, отрезок до первой точки считается от него и тоже тратит бюджет
server/routers/       /api/v1: places, categories, chips, routes/generate, routes (сохранённые маршруты),
                      guides (справка по месту), events (аналитика), metrics/funnel (метрики пилота)
server/analytics.py   семь метрик §8 из принятых событий: доли считаются по сессиям, время до маршрута —
                      медианой, пустая выборка даёт null, а не 0
server/cors.py        CORS для браузерных запросов Mini App (CORS_ALLOW_ORIGINS)
server/app.py         FastAPI: lifespan, POST /webhook, /health
scripts/export_openapi.py
                      генерация DATA-API.yaml из живого приложения (--check для CI)
frontend/             Mini App (React + Vite): онбординг → настройки + старт → маршрут на карте → навигация
main.py               единая точка входа: --mode=webhook|polling|setup-webhook
```

Запросы к MAX идут на `https://platform-api2.max.ru` (токен в заголовке `Authorization`, сырой
строкой — query-параметр `access_token` больше не поддерживается).

## Запуск одной командой (Docker)

```bash
git clone https://github.com/san4EZzzZZZ/hackaton_max && cd hackaton_max
docker compose up --build
```

Этого достаточно: поднимаются оба локальных компонента — API бота и Mini App, — `.env` создавать не
нужно и рабочие ключи не нужны вовсе. Compose подставляет заглушку в `BOT_TOKEN`, выключает
`AUTO_SETUP` (иначе старт стучался бы в MAX чужим токеном) и оставляет `INGEST_TOKEN` пустым
(эндпоинты записи каталога тогда отвечают `503`). Приложение валидирует окружение на импорте, поэтому
пустой `BOT_TOKEN` обрывает старт — заглушка в compose стоит ровно для того, чтобы «одна команда»
оставалась одной командой.

Дальше открываются:

- **Mini App** — <http://localhost:8081>. Тот же nginx проксирует `/api/` на сервис `bot`, поэтому
  фронт зовёт относительный `/api/v1`: CORS и переменные сборки не нужны.
- **API и документация** — <http://localhost:8080/docs> (он же доступен как <http://localhost:8081/docs>).
- **Проверка готовности** — <http://localhost:8080/readyz> обязан ответить `200`.

`docker compose up` остаётся на переднем плане и печатает логи; для фона — `docker compose up -d`
(остановка и повторный запуск описаны в конце). Пересборка не трогает ни каталог, ни базу: места
читаются из `data/` этой папки (монтируется в контейнер), а записанное — сохранённые маршруты и события
аналитики — живёт в именованном томе `bot-state` и переживает `--build` и `down`.

Боевой стек этого же решения — HTTPS-домен <https://max.chestnyidiplom.ru> (Mini App в корне сайта, API
в `/api/v1`); его сборка лежит в `tools/deploy/docker-compose.yml` и к локальному запуску отношения не имеет.

## Запуск без Docker (локальная разработка)

Нужен только токен, публичный HTTPS не требуется:

```bash
python -m venv .venv && .venv\Scripts\activate   # Linux: source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env                              # Windows: copy; вписать BOT_TOKEN
python main.py --mode=polling
```

Зависимости закреплены через `==` — и в `requirements.txt`, и в `dev-requirements.txt`: образ и CI
перестают зависеть от того, какая версия FastAPI или SQLAlchemy вышла вчера. Версии подобраны так,
чтобы под них были готовые колёса и для образа (`cp312` + `manylinux_2_28`), и для локальной Windows
(`cp313` + `win_amd64`). Как поднимать пакет — описано комментарием в шапке `requirements.txt`.

Корневой сертификат Минцифры уже лежит в репозитории (`certs/russian-trusted-root-ca.pem`), он
подмешивается к системным корням на лету — отдельный шаг не нужен.

## Порты

| Порт | Кто слушает | Где | Что отдаёт |
| --- | --- | --- | --- |
| `8080` | `bot` (uvicorn) | контейнер и хост (`SERVER_PORT`) | `/api/v1/*`, `POST /webhook`, `/health`, `/readyz`, `/docs`, `/openapi.json` |
| `8081` | `miniapp` (nginx) | контейнер слушает `80`, на хост вешается `MINIAPP_PORT` | статика Mini App + прокси `/api/`, `/docs`, `/health`, `/readyz` на `bot:8080` |
| `5173` | `vite dev` | только запуск без Docker | фронт с прокси `/api` → `VITE_BACKEND_URL` (по умолчанию `:8080`) |
| `4173` | `vite preview` | только запуск без Docker | та же прод-сборка из `dist/`, что собирается в контейнер |
| `443` | nginx на сервере | только боевой прогон | HTTPS для MAX: Mini App в корне сайта, `/api/` → `127.0.0.1:8080` |

Локально заняты два порта — 8080 и 8081; оба настраиваются без правки файлов
(`SERVER_PORT`, `MINIAPP_PORT` в `.env`). Ни БД, ни очереди, ни кэш-сервер локального порта не требуют:
SQLite — файл, в Docker он лежит в томе `bot-state`, без Docker по умолчанию в `data/bot.db`.

## Зависимости

Python 3.12 (образ `python:3.12-slim`), Node 20 для сборки фронта. Ни apt-пакетов, ни сборки из
исходных кодов: всё ставится колёсами.

| Набор | Файл | Как ставится |
| --- | --- | --- |
| рантайм | `requirements.txt` (закреплён `==`) | `pip install -r requirements.txt`; в образе — слой builder → `--prefix=/install` |
| разработка (pytest, PyYAML) | `dev-requirements.txt` (закреплён `==`) | `pip install -r dev-requirements.txt`; в рантайм-образ **не** попадает |
| фронтенд | `frontend/package.json` + `frontend/package-lock.json` | `npm ci` в контейнере (по лок-файлу), локально — `npm install` |

Закрепление версий — не формальность: `docker build` без лок-файла зависел от того, какая версия
FastAPI или SQLAlchemy вышла вчера. Пины подобраны так, чтобы под них были готовые колёса и для образа
(`cp312` + `manylinux_2_28`), и для локальной Windows (`cp313` + `win_amd64`); способ поднять пакет
описан комментарием в шапке `requirements.txt`.

Сборка спроектирована под лимит «не дороже пяти минут»: тяжёлые шаги отделены от исходников —
`pip install` и `npm ci` копируют только манифесты зависимостей и пересобираются лишь при их изменении,
`COPY . .` идёт после них, а `.dockerignore` не пускает в контекст `frontend/`, `tools/`, `.venv/`,
`data/*.db` и `node_modules`. Ни apt-пакетов с билд-тулзами, ни сборки из исходных кодов в образах нет:
`python:3.12-slim` дописывает только `ca-certificates`, `nginx:1.27-alpine` ничего не устанавливает.

## Внешние сервисы и интеграции

Ни один из них не требует платного аккаунта; ключ нужен только у MAX.

| Сервис | Зачем | Ключ | Переменные |
| --- | --- | --- | --- |
| `https://platform-api2.max.ru` | бот: приём событий, отправка сообщений, меню команд, подписка на вебхук | `BOT_TOKEN` из кабинета business.max.ru | `BOT_TOKEN`, `BOT_API_URL`, `AUTO_SETUP` |
| `https://tiles.openfreemap.org` | подложка карты (стиль Positron, MapLibre) | нет | — (шифтится во фронтенде) |
| `https://*.wikimedia.org` | фотографии мест в карточках и справках | нет | — (ссылки лежат в `data/*.json`) |
| `https://routing.openstreetmap.de/routed-foot` | длина пешеходных переходов для линии маршрута | нет | `OSRM_URL`, `OSRM_TIMEOUT` |
| `https://nominatim.openstreetmap.org` | центр города и его прямоугольник (автокаталог) | нет, но нужен `User-Agent` с контактом | `NOMINATIM_URL`, `INGEST_USER_AGENT` |
| Overpass (OSM) | объекты семи категорий по тегам | нет | `OVERPASS_URL` (боеное зеркало — `https://maps.mail.ru/osm/tools/overpass/api/interpreter`) |
| `https://query.wikidata.org/sparql` | русское название, описание, наличие статьи | нет | `WIKIDATA_SPARQL_URL` |
| `https://commons.wikimedia.org/w/api.php` | превью 960 px с лицензией и автором | нет | `COMMONS_API_URL` |

Бот обращается в MAX, только если включён `AUTO_SETUP` или ему реально пишут; локальный прогон
`docker compose up` к MAX не стучится. Обращения к OSRM/Nominatim/Overpass — из процесса генерации
маршрута и из `python -m ingest`, они не блокируют друг друга и имеют короткие таймауты: если OSRM
молчит, линия честно становится хордой с `geometry_source: "straight_line"`.

TLS: MAX отдаёт цепочку, корень которой — «Russian Trusted Root CA» УЦ Минцифры, которого нет ни в
`certifi`, ни в базовом образе. Корень лежит в `certs/` и подмешивается к системным, поэтому проверка
сертификата остаётся строгой (`SSL_VERIFY=false` не нужен).

## Клавиатуры в MAX: что реально поддерживает API

MAX не знает про Telegram-подобную `reply_markup`/постоянную клавиатуру у поля ввода. Есть три
нативных механизма, и все три здесь используются:

| Механизм | Где отображается | Реализация |
| --- | --- | --- |
| `attachments/type=inline_keyboard` | под сообщением, до 30 рядов | `bot/keyboards.py:mini_app_keyboard()` |
| кнопка мини-приложения в настройках бота | у поля ввода («Открыть/Старт/Играть») | включается в кабинете MAX |
| `PATCH /me/commands` (меню команд) | у поля ввода, как постоянная клавиатура | `bot_commands()` + `AUTO_SETUP=true` |

Кнопка запуска Mini App — тип `open_app` с полем `web_app` (нужна привязка мини-приложения к боту).
Если `MINI_APP_URL` пустой, билдер честно откатывается на `link`-кнопку с диплинком
`https://max.ru/<BOT_USERNAME>?startapp=<payload>`, и кнопка продолжает работать.

Жёсткие ограничения, проверенные на живом API (нарушение = `400 proto.payload`, а не тишина):

| Правило | Как соблюдается в коде |
| --- | --- |
| в одном сообщении ровно **один** `inline_keyboard` | `merge_keyboards()` склеивает ряды; `SendMessagePayload` не даст собрать два |
| `open_app` без `web_app` не проходит («Field 'webApp' cannot be null») | `OpenAppButton.web_app` обязателен в модели, билдер падает на `link` |
| `open_app.payload` — только `[A-Za-z0-9_-]` (`start:menu`, URL, `a.b` — отказ) | `sanitize_app_payload()` + `pattern` в модели |
| `callback.payload` свободный (`action:refresh`, JSON, кириллица) | как есть |
| `POST /answers` требует тело: `message` или `notification` (`{}` → `400 proto.payload`) | `CallbackAnswerPayload.message` обязателен; тап отвечает `Context.answer()` — MAX подменяет сообщение с кнопками, при отказе уходит новое сообщение |
| текст ≤ 4000 символов, ≤ 2 сообщения в секунду в диалог | `max_length` в модели + `_throttle()` в клиенте |

## Конфигурация

| Переменная | Назначение |
| --- | --- |
| `BOT_TOKEN` | токен бота из business.max.ru |
| `BOT_API_URL` | по умолчанию `https://platform-api2.max.ru` |
| `BOT_USERNAME` | используется для диплинка мини-приложения |
| `MINI_APP_URL` | адрес Mini App для кнопки `open_app` |
| `BOT_WEBHOOK_URL` / `PUBLIC_BASE_URL` | адрес вебхука (второй — базовый, `/webhook` добавится сам) |
| `WEBHOOK_SECRET` | MAX вернёт его в заголовке `X-Max-Bot-Api-Secret`; обязателен с вебхуком |
| `DATABASE_URL` | `sqlite+aiosqlite:///data/bot.db` или `postgresql+asyncpg://...`; в Docker-стеке по умолчанию `state/bot.db` — том, доступный контейнеру на запись |
| `SSL_CA_BUNDLE` / `SSL_VERIFY` | доп. доверенный корень MAX (уже лежит в `certs/`) / строгость TLS |
| `AUTO_SETUP` | регистрировать меню команд и подписку при старте; в локальном стеке выключено намеренно |
| `POLLING_TIMEOUT` / `POLLING_LIMIT` | параметры long polling (0..90 / 1..1000) |
| `SERVER_HOST` / `SERVER_PORT` | адрес и порт API; контейнер всегда слушает 8080, переменная выбирает порт на хосте |
| `MINIAPP_PORT` | порт, на `docker compose up` вешает Mini App (по умолчанию 8081) |
| `CORS_ALLOW_ORIGINS` | список origin'ов через запятую, которым разрешено звать `/api/v1` из браузера; пусто — `*` |
| `OSRM_URL` / `OSRM_TIMEOUT` | пешеходный роутер для линии маршрута (пусто — хорды и `geometry_source=straight_line`) |
| `INGEST_TOKEN` | заголовок `X-Ingest-Token` для эндпоинтов автокаталога; пусто — они отвечают `503` |
| `INGEST_USER_AGENT` / `INGEST_REQUEST_GAP` | контакт для OSM-сервисов и пауза между запросами к одному хосту |
| `INGEST_TIMEOUT` / `INGEST_HTTP_RETRIES` | таймаут и ретраи тяжёлых запросов к Overpass |
| `INGEST_MAX_PLACES_PER_CITY` / `INGEST_MAX_PER_CATEGORY` / `INGEST_CORE_RADIUS_KM` | срезы автокаталога: город, категория, дистанция до центра |
| `OVERPASS_URL` / `NOMINATIM_URL` / `WIKIDATA_SPARQL_URL` / `COMMONS_API_URL` | адреса открытых источников каталога |
| `INGEST_CITIES_FILE` | список городов, который обходит `python -m ingest --all` |
| `VITE_API_URL` / `VITE_BACKEND_URL` | не рантайм: переменные **сборки** фронта (адрес API) и **dev-прокси** |

Обязательных переменных две, и обе — только для демо в мессенджере: `BOT_TOKEN` (иначе приложение не
стартует) и `WEBHOOK_SECRET` (иначе `/webhook` принимает неаутентифицированные полезные нагрузки).
Порядок получения: `business.max.ru` → Чат-боты → Настройки → скопировать токен сырым (без `Bearer`);
`WEBHOOK_SECRET` — любая своя строка 5–256 символов; `INGEST_TOKEN` —
`python -c "import secrets; print(secrets.token_urlsafe(32))"`. Всё остальное имеет значения по
умолчанию, и `docker compose up` не просит ни одной из них.

`VITE_API_URL` по умолчанию пуст, и это важно: фронт зовёт относительный `/api/v1`, поэтому один и тот
же собранный артефакт работает и за nginx'ом локального стека, и на бою — подменять адрес переменной
сборки не нужно.

Смена SQLite → PostgreSQL не требует кода: только `DATABASE_URL` (движок сам подставит
`asyncpg`, upsert работает на обеих диалектах).

## TLS

MAX отдаёт цепочку, корень которой — «Russian Trusted Root CA» УЦ Минцифры (НУЦ Госуслуг). Такого
корня нет ни в хранилище Windows, ни в базовом образе (`unable to get local issuer certificate` —
проверено локально). Корень лежит в `certs/russian-trusted-root-ca.pem` и подгружается к корням
`certifi`: проверка сертификата остаётся строгой и на Windows, и в контейнере, `SSL_VERIFY=false`
не требуется.

Скачан по адресу AIA из промежуточного сертификата MAX, оба зеркала отдали байт-в-байт один файл:

```
http://nuc-cdp.digital.gov.ru/cdp/rootca_ssl_rsa2022.crt
http://nuc-cdp.voskhod.ru/cdp/rootca_ssl_rsa2022.crt
sha256: 936a43fea6e8e525bcc0f81acd9c3d21b4fc4b9b68acea7906d698005afc6504
fingerprint: D2:6D:2D:02:31:B7:C3:9F:92:CC:73:85:12:BA:54:10:35:19:E4:40:5D:68:B5:BD:70:3E:97:88:CA:8E:CF:31
```

Перед заменой файла сверьте отпечаток с публикацией УЦ. Свой путь — `SSL_CA_BUNDLE`; если файл не
найден, клиент честно предупреждает в лог и остаётся только системное хранилище.

Отдельно: **с 25 мая 2026 MAX не принимает вебхуки по HTTP и самоподписанные сертификаты** —
нужен валидный сертификат от доверенного ЦС (в том числе Минцифры) на 443 порту.

Контракт для фронтенда — `DATA-API.yaml` в корне (он же в JSON — `openapi.json`, он же живой на
`/docs` и `/openapi.json`). Он не правится руками: после любого изменения эндпоинтов пересоберите его
из живого приложения (`python scripts/export_openapi.py`) и коммитьте вместе с кодом, а CI сверяет
файл с кодом через `--check`. Первым блоком в обоих файлах лежит `x-check` — версия конфигурации,
наименование решения и команды, базовый HTTPS-адрес, тестовые учётные записи, тестовые данные и
перечень обязательных проверок; для каждого эндпоинта там указаны метод, путь, параметры, роль
пользователя, ожидаемый статус-код и обязательные поля ответа.

Экран «выбрать город → чипы/категории → время и бюджет → маршрут» собирается тремя запросами, и все поля
в последнем уже пришли из первых двух:

```bash
curl localhost:8080/api/v1/cities                       # какие города есть в данных и что в них категорий
curl "localhost:8080/api/v1/chips?city=Казань"          # чипы этого города; пустого чипа в ответе нет
curl -X POST localhost:8080/api/v1/routes/generate \
  -H 'content-type: application/json' \
  -d '{"city":"Казань","tags":["culture"],"categories":["Музей","Галерея"],
       "duration_hours":3,"max_budget":800,"start_lat":55.796,"start_lon":49.106}'
```

`tags` — `id` из `/chips` (внутри списка ИЛИ, между `tags` и `categories` — И), `max_budget` принимает и
короткое имя `budget`. Ничего не подошло — `404` с текстом, а не пустой маршрут: город, которого нет в
данных, и город, где фильтр не находит мест, отвечают одинаково.

**Линия маршрута приходит в том же ответе.** Каждая точка несёт `geometry_from_prev` — переход к ней по
пешеходной сети (координаты GeoJSON, `[lon, lat]`), и `walk_distance_m_from_prev` — сколько метров в этом
переходе человек реально пройдёт. Один запрос к публичному OSRM на всю цепочку (точки как via), без ключа
и без своего роутера; `server/geometry.py` режет ответ на leg'и по waypoint'ам. Если сервер маршрутов не
ответил или выключен (`OSRM_URL=`), линия остаётся — но это хорда между маркерами, и
`geometry_source: "straight_line"` говорит об этом вслух, а `walk_distance_m_from_prev` при этом `null`:
прямую измерить не у кого.

Минут это не касается. `travel_minutes_from_prev`, `arrival_offset_minutes` и бюджет остаются моделью
планировщика: маршрут, сошедшийся в два часа при сборке, должен возвращаться двухчасовым и когда OSRM
добавил к переходу двести метров дворов. Пешеходный ETA демо-инстанса взят из воздуха — на 809 метров он
отдаёт 107 секунд, то есть 27 км/ч; доверять такому числу значило бы обещать посетителю время, которого
не существует.

## Тестовые данные и учётные записи

**Учётных записей нет ни у кого, и это не недоработка:** у HTTP-API нет ни сессий, ни токенов, ни куки,
поэтому логин/пароль для проверки не нужны — в том же виде, в каком решение стоит на бою. Единственный
секрет в контуре — `INGEST_TOKEN` для двух эндпоинтов, которые переписывают каталог; локальный стенд
оставляет его пустым, и они отвечают `503`.

| Роль | Что делает | Как войти |
| --- | --- | --- |
| гость | смотрит каталог, собирает и проходит маршрут, сохраняет прогулку | не требуется |
| редактор каталога | `POST /api/v1/admin/ingest`, `GET .../ingest/status` | заголовок `X-Ingest-Token`, значение — `INGEST_TOKEN` |
| оператор бота | пишет боту в MAX, получает клавиатуру | свой аккаунт MAX + настоящий `BOT_TOKEN` |

Тестовые данные **в репозитории, их не надо генерировать**: `data/places.json` — 43 вручную сверенных
места Ростова, `data/places.d/rostov-na-donu.json` — 47 мест, собранных автокаталогом,
`data/place_guides.json` — 8 справок для чтения, `data/cities.json` — города, по которым автокаталог
умеет ходить. Клон получает один город с 90 точками: Казань и Сочи собраны тем же пайплайном, но в
качестве эксперимента остаются на бою и в репозиторий не коммитятся.

Ничего из этого не читается из интернета и не пишется в базу во время проверки: каталог и справки —
только файлы, база (`data/bot.db`) нужна лишь для сохранённых маршрутов и событий аналитики.

Свои тестовые данные создаются за два запроса — сохранённый маршрут и воронка пилота:

```bash
curl -s -X POST localhost:8080/api/v1/events -H 'content-type: application/json' \
     -d '{"name":"miniapp_open","session_id":"review-0001"}'
curl -s "localhost:8080/api/v1/metrics/funnel?days=14"
```

Событийные имена взяты из продуктовой проработки дословно (`miniapp_open`, `route_setup_started`,
`route_generated`, `route_started`, `poi_opened`, `route_completed`, `route_rated`), и метрики
начинают наполняться, как только их прислать: без наблюдений `GET /metrics/funnel` отдаёт `null`,
а не `0`. Удалить тестовые данные целиком: в Docker — `docker compose down -v` (вместе с томом
`bot-state`), без Docker — `rm -f data/bot.db data/bot.db-wal data/bot.db-shm` при остановленном
процессе.

## Пошаговый сценарий проверки

Локально: `docker compose up --build` из раздела «Запуск одной командой», дальше всё доступно с двух
портов. На бою те же запросы идут на `https://max.chestnyidiplom.ru` (API — с префиксом `/api/v1`,
Mini App — корень сайта). Все шаги — про чистый клон, ожидаемые числа берутся из каталога репозитория.
На Windows в `curl -d` кириллица доходит только через файл (`--data-binary @body.json` с UTF-8);
в Linux и macOS примеры ниже работают как написаны.

1. **Стек поднялся.** `docker compose ps` — оба сервиса `running`, `bot` в статусе `healthy`.
   `curl -i localhost:8080/readyz` → `200`; `curl -i localhost:8080/health` → `200` с числом
   пользователей. Ожидаемое в логе `bot`: `Loaded 90 places from 2 file(s)`.
2. **Контракт на месте.** `localhost:8080/docs` отдаёт Swagger, `curl localhost:8080/openapi.json` —
   JSON со списком эндпоинтов. В репозитории лежат `DATA-API.yaml` и `openapi.json`; файл `x-check`
   в их начале — версия конфигурации, название решения и команды, базовый HTTPS-адрес, перечень
   обязательных проверок с методами, путями, параметрами, ролью и ожидаемыми кодами.
3. **Города.** `curl localhost:8080/api/v1/cities` → `200`, массив из одного элемента:
   `Ростов-на-Дону`, `place_count: 90`, семь категорий.
4. **Чипы.** `curl "localhost:8080/api/v1/chips?city=Ростов-на-Дону"` → `200`, пять чипов с
   ненулевыми счётчиками («Взять кофе» 11, «Культура» 37, «Погулять в парке» 38, «Перекусить» 9,
   «Красивые фото» 58). Чипа с нулём мест в ответе быть не должно.
5. **Каталог с фильтром.** `curl "localhost:8080/api/v1/places?city=Ростов-на-Дону&category=Музей&limit=5"`
   → `200`, ровно 5 элементов, у каждого `id`, `title`, `location.lat`/`lon`, `category`, `price`,
   `visit_duration_minutes`; в заголовках — `X-Total-Count` (размер выборки до `limit`) и `X-Offset`.
   Пустая выборка (`category=Отель`) → `200 []`, не `404`.
6. **Генерация маршрута.**

   ```bash
   curl -i -X POST localhost:8080/api/v1/routes/generate -H 'content-type: application/json' \
        -d '{"city":"Ростов-на-Дону","tags":["culture"],"duration_hours":3,"max_budget":800}'
   ```

   → `200`, 5 остановок, `total_duration_minutes: 135` (это 85 % от трёх часов: заказанные 180 минут
   планировщик целиком не тратит), `slack_minutes: 45`, `total_distance_m: 1028`,
   `stops[i].order` идёт 0..4, у каждой остановки `place.title` совпадает с каталогом, а
   `geometry_from_prev` — массив пар `[lon, lat]`. `geometry_source: "osrm"`, если пешеходный роутер
   ответил, и `"straight_line"` вместе с `walk_distance_m_from_prev: null`, если нет; минуты при этом
   не меняются.
7. **Старт и границы бюджета.** Тот же запрос с `start_lat`/`start_lon` — `47.2219` и `39.7139`, эти
   же координаты лежат в параметрах проверки `x-check.mandatory_checks` — → `200`, а
   `stops[0].travel_minutes_from_prev` и `distance_m_from_prev` считают путь от старта, то есть nonzero.
   `max_budget: 0` и редкая категория → `404` с текстом, а не пустой маршрут; город, которого нет в
   данных, отвечает так же. Половина пары координат → `422`.
8. **Линия маршрута — не выдумка.** В ответе шага 6 сумма длин `walk_distance_m_from_prev` лежит в
   разумных пределах для 1 км прогулки, а координаты перехода не уходят за город: это путь по
   тротуарной графе, а не прямая между маркерами.
9. **Справка по месту.** `curl localhost:8080/api/v1/guides` → 8 записей-указателей;
   `curl localhost:8080/api/v1/places/theatre-square/guide` → `200` с `history` (2–3 абзаца),
   `highlights` (3–5 фактов), `media[].credit` и `media[].license`, `nearby` (до 4 точек);
   места без справки → `404` с текстом «ещё нет» — это очередь, а не ошибка.
10. **Сохранение переживает перезапуск.** `curl -i -X POST localhost:8080/api/v1/routes` телом ответа
    шага 6 → `201` с целым `route_id`; `curl localhost:8080/api/v1/routes?limit=5` → `200`, свежий
    маршрут первый. Затем `docker compose restart bot` и повтор списка — запись на месте (база живёт в
    томе `bot-state`, а не в слое контейнера).
11. **Mini App в браузере.** Открыть `http://localhost:8081`: онбординг → «Настроить прогулку» →
    город, чипы, время и бюджет → «Показать маршрут». На экране карты — маркеры по порядку и
    нарисованная линия переходов; «Начать прогулку» → навигация, «Я на месте» открывает карточку точки
    со справкой, «Завершить прогулку» показывает итог (пройдено метров, затрачено времени против
    плана). Консоль браузера без ошибок; в Network все вызовы `/api/v1/*` идут на тот же origin, что
    открыт в браузере (наружу ходят ещё тайлы `tiles.openfreemap.org` и снимки `*.wikimedia.org`), а
    `VITE_API_URL` при сборке задавать не нужно.
12. **Аналитика.** Шаги выше + `POST /api/v1/events` из предыдущего раздела → `201`, а
    `GET /api/v1/metrics/funnel` начинает отдавать числа там, где был `null`.
13. **Остановка и повторный запуск** — раздел ниже; после `down` + `up` каталог и сохранённые маршруты
    те же.

Для демо в мессенджере (нужен настоящий `BOT_TOKEN` и публичный HTTPS): `AUTO_SETUP=true`,
`docker compose exec bot python main.py --mode=setup-webhook`, затем в MAX написать боту — в ответ
приходит приветствие и inline-клавиатура с кнопкой Mini App.

## Ожидаемое поведение (примеры)

| Запрос | Ответ | Почему так |
| --- | --- | --- |
| `GET /api/v1/places?city=Ростов&category=Отель` | `200 []` | коллекции по фильтру не существует — это пустая полка, не ошибка |
| `POST /api/v1/routes/generate {"city":"Кот-на-Дону",...}` | `404 {"detail":"…"}` | маршрута не существует; неизвестный город и город без мест отвечают одинаково |
| `POST /api/v1/routes/generate {"duration_hours":2,"start_lat":47.2}` | `422` | одной координаты достаточно для точки? нет: `start_lat` требует `start_lon` |
| `POST /api/v1/routes/generate {"budget":800}` | `200` | короткое имя `budget` принимается наряду с `max_budget` |
| `POST /api/v1/routes` телом ответа генератора + `{"user_id":7}` | `201` с целым `route_id` | тело развёрнуто верхним уровнем; обёртка `route` в запросе — `422` |
| `GET /api/v1/metrics/funnel` на пустой выборке | `200`, значения `null` | «никто не начинал» и «все начали, никто не закончил» — разные новости |
| `POST /api/v1/admin/ingest` без `X-Ingest-Token` | `503` | эндпоинт переписывает каталог целиком; без токена он выключен |
| `GET /health` при закрытой базе | `200` | на него висит `HEALTHCHECK` контейнера; готовность измеряет `/readyz` (`503`) |
| `city=ростов-на-дona`-подобные варианты | один и тот же город | сопоставление нестрогое: `Ростов`, `Ростов на Дону`, `ростов-на-Дону` |

Ответы с кодом `503` называют в `detail` файл или подсистему, которая не читается, — «битый
`data/place_guides.json`» не ломает `/places` и генератор маршрутов.

## Автокаталог мест (`ingest/`)

Подсистема, которая сама находит реальные места в выбранном городе, чтобы не писать их руками для
каждой новой точки карты.

Источники — только открытые, без ключа и без аккаунта:

| Откуда | Что берёт |
| --- | --- |
| Nominatim | центр города, его `bbox` и osm-идентификатор |
| Overpass (OSM) | объекты по тегам семи категорий: Музей, Театр, Галерея, Парк, Памятник, Архитектура, Кафе |
| Wikidata | русское название, описание, ссылка на commons-файл, наличие статьи в ру-Вики |
| Wikimedia Commons | превью 960 px плюс лицензия и автор — их Commons требует показывать |

Куда пишется: **отдельный файл на город** — `data/places.d/<город>.json` (в git не попадает). В проде
каталог живёт в примонтированном томе (`tools/deploy/docker-compose.yml`: `./app/data:/app/data`),
поэтому собранные города переживают пересборку образа и автодеплой. `data/places.json` — руками
выверенный Ростов, — не затрагивается никогда. Каталог сервера читает обе папки, при этом сид идёт
первым: если идентификаторы совпадут, победит проверенная руками запись.

Запуск:

```bash
# посчитать и посмотреть, ничего не записывая
python -m ingest --city Казань --dry-run
# записать 30 мест в data/places.d/kazan.json
python -m ingest --city Казань --limit 30
# все города из data/cities.json
python -m ingest --all
```

или по HTTP (то же самое, асинхронно): `POST /api/v1/admin/ingest` с заголовком `X-Ingest-Token`,
затем `GET /api/v1/admin/ingest/status`. Без `INGEST_TOKEN` оба отдают 503 — эндпоинт единственный в
API, который что-то записывает.

Что важно знать, если вы это читаете:

- **Рейтинг не выдуман.** В OSM нет оценок посетителей, поэтому `rating` — функция от
  «сколько мира написало об этом месте» (статья в Вики, элемент Викиданных, фото, `tourism=attraction`),
  и в `provenance.rating_basis` это записано прямо как `attestation`.
- **Непроверенные поля помечены.** Цена, «Пушкинская карта», длительность визита, часы работы и адрес,
  которых нет в источнике, перечислены в `provenance.unverified_fields` — ровно как в ручном сиде.
- **Прогон перезаписывает файл города целиком**, а не дописывает в него: удалённый в OSM объект не
  должен вечно жить в каталоге. Поэтому сначала `--dry-run`, потом запись.
- **Упадает категория, а не город.** 504 от Overpass по одной категории — это строка в `failures`
  отчёта, остальные категории город получит.
- **Не стучитесь чаще.** `INGEST_REQUEST_GAP` (по умолчанию 5 с) — пауза между запросами к одному
  хосту: открытый Overpass режет 429 и queued-запросы, а Nominatim по правилам просит не чаще одного
  запроса в секунду. `INGEST_USER_AGENT` должен содержать контакт.
- **Дальше `INGEST_CORE_RADIUS_KM` (25 км от центра) место не публикуется.** Nominatim отвечает
  прямоугольником, а прямоугольник вокруг Сочи доставал водопад в 31 км и виадук в 48 — планировщик
  затем звал человека идти туда пешком. Ограничение можно поднять для города, где достопримечательности
  правда разбросаны так далеко.
- **Длительность остановки — время прогулки, а не всей экспозиции.** В OSM этого поля нет, и число
  придумано здесь: Музей 45 мин, Театр 90, Галерея 45, Парк 60 (корректируется по площади), Памятник 20,
  Архитектура 20, Кафе 30. С 90 минутами на музей запрос «Культура, 2 часа» давал одну остановку. Поле
  по-прежнему перечислено в `unverified_fields`.
- **Чип живёт внутри категории.** `Кафе` отвечает на два разных вопроса («взять кофе» и «перекусить»), и
  по одним только свидетельствам слоты категории заполняют рестораны: у кофеен нет ни статьи в Вики, ни
  фото. Поэтому `INGEST_MAX_PER_CATEGORY` чередует две группы, а общий лимит города (`--limit`) раздаётся
  по одному объекту от категории за круг — иначе «60 мест, отсортированных по свидетельству» съедают
  категорию целиком. Живой Казанский прогон показал обе половины: сначала под чип кофе осталось одно
  место, потом, после чередования, — тоже одно, потому что кофейни проигрывали уже общий срез.
- **Природа не архитектура.** `tourism=attraction` висит и на водопадах, и на пляжах — в `Архитектуру`
  они не попадают (смотровая на вершине остаётся: она приходит в `Парк`).

## Mini App (frontend/)

React 18 + Vite, CSS-модули, без сторонних UI-библиотек. Фронтенд **не меняет бэкенд**: только
существующие эндпоинты `/api/v1` из `DATA-API.yaml`. Четыре экрана: онбординг по макету → выбор
времени 1–4 ч, чипов и точки старта (поиск по каталогу — `/places`) → маршрут на карте MapLibre с
нарисованной линией переходов → навигация: «Я на месте» открывает карточку места со справкой
(`/places/{place_id}/guide`), «Завершить прогулку» подводит итог — пройденные метры и затраченное
время против плана. Состояния loading/error/empty, safe-area и haptics при открытии внутри WebView
MAX/Telegram (feature-detection в `src/lib/messenger.js`).

Линия берётся из того же ответа API (`geometry_from_prev`, `geometry_source`): пунктиром и серым
рисуются только переходы, которые роутер не измерил, — фронт не додумывает тротуары и не пересчитывает
тайминги. Что ещё не делалось: тёмная тема, тесты, перестановка точек (иконка ⇄ пока декоративная).

Фронт в локальном стеке отдаёт контейнер `miniapp` (см. «Запуск одной командой»): та же прод-сборка,
nginx, `/api` на том же origin — отдельно фронтенд поднимать не нужно. Ниже — как запустить его
поверхностями без Docker, тремя процессами:

```bash
# 1. API бэкенда (из корня репозитория, .env с BOT_TOKEN не обязателен для одних только /api)
python main.py --mode=webhook            # или: uvicorn server.app:app --port 8080

# 2. Mini App: http://localhost:5173, /api проксируется на VITE_BACKEND_URL (по умолчанию :8080)
cd frontend && npm install && npm run dev

# 3. (только для демо в мессенджере) HTTPS-туннель на фронтенд
cloudflared tunnel --url http://localhost:5173
```

Прод-сборка статики — `npm run build` в `frontend/` (результат в `dist/`, адрес API задаётся
переменной сборки `VITE_API_URL`). `npm run preview` поднимает собранный `dist` на :4173 с тем же
прокси `/api` — так прод-сборка (и особенно worker MapLibre, который ломается только на ней)
проверяется локально, без выката.

### Ограничение MAX: регистрация ссылок

Проверено живым запросом (`tools/test_buttons.py`, не коммитится): кнопка `open_app` с URL,
не привязанным к боту в кабинете `business.max.ru`, роняет всё сообщение с
`404 not.found / Link not found (LinkPK ... space=TAMTAM)`. Обычные `link`-кнопки принимают
любой HTTPS-URL. Поэтому в `.env`:

- `MINI_APP_URL` — адрес мини-приложения **после** привязки в кабинете; тогда «🧭 Открыть
  навигатор» открывается нативным WebView MAX;
- без привязки `MINI_APP_URL` держится закомментированным, а `PUBLIC_BASE_URL` указывает на
  публичный HTTPS-адрес фронтенда — «🌐 Веб-версия» открывает то же приложение в браузере.

Для туннельного URL нужен `allowedHosts: ['.trycloudflare.com']` в `vite.config.js` (уже
настроено), а адрес меняется при каждом перезапуске туннеля — после смены обновите `.env` и
перезапустите бота.

```bash
pip install -r dev-requirements.txt
python scripts/export_openapi.py            # перегенерировать
python scripts/export_openapi.py --check    # проверка, которая будет крутить CI
```

Тесты бэкенда — `pytest`, они не трогают ни `.env`, ни живую базу (`data/pytest.db`), ни MAX API:

```bash
python -m pytest tests -q
```

CI (`.github/workflows/ci.yml`) на каждом PR прогоняет тесты на Python 3.12, сверяет `DATA-API.yaml` с
кодом и собирает образ.

Семантика ответов, на которую стоит опираться:

- `city` сопоставляется нестрого: `Ростов`, `ростов-на-Дону`, `Ростов на Дону` и `Ростов-на-Дона` — один
  и тот же город. Достаточно, чтобы введённые слова были началом названия из каталога.
- `GET /places` с пустой выборкой отдаёт `200 []` (коллекция по фильтру пуста — это не ошибка), а
  `POST /routes/generate` — `404`, потому что маршрута не существует.
- Бюджет в `/routes/generate` ограничивает **суммарную** стоимость маршрута и принимается под именем
  `max_budget` или `budget`.
- Переходы считаются по **пешеходному** темпу: `travel_minutes_from_prev` — это 4,8 км/ч плюс три минуты
  запаса на выход из здания, а `distance_m_from_prev` — расстояние от предыдущей точки **по прямой**, не
  длина обхода по тротуарам. Если карта посчитает путь сама, её ETA будет больше наших минут: это не
  расхождение, а два разных вопроса — «сколько планируем мы» и «сколько идёт навигатор».
- `total_duration_minutes` и `total_distance_m` — суммы, которые клиент мог бы сложить из `stops` сам, но
  не должен; `slack_minutes` — сколько минут заказанного времени остаётся свободным.
- Планировщик **не тратит запрос целиком**: 15 % заказанного времени остаются резервом, а не точкой.
  Очереди, закрытая дверь и «один экспонат, который оказался на час» не лежат в
  `visit_duration_minutes`, и маршрут, забитый до последней минуты, куда их денет — только обещанием,
  что всё успеется. Поэтому четыре часа — это план на 204 минуты (на практике 192: семь точек, 2,35 км),
  а `slack_minutes` у такого ответа не меньше 36. Пилот меряется соответствием времени в пределах ±15 %,
  и без резерва этой метрики не достичь. Экран обязан показывать запас («запас 36 мин»), а не прятать его:
  иначе гость видит «3 ч 12 мин» там, где просил четыре часа.
- Точки маршрута не ставят ближе **150 метров** друг к другу, а при равном числе остановок планировщик
  берёт тот набор, который покрывает больше улиц. Причина в каталоге: у Театральной площади кофейня стоит
  в метрах от памятника, и без этого правила четыре часа давали 1,4 км пути девятью точками вместо 3,0 км
  восемью. Меньше точек ради прогулки по городу, а не по одной аркаде, — осознанный размен; резерв времени
  убирает из этих восьми ещё одну точку и даёт 2,35 км семью.
- И не дальше **2,5 километров** между соседними точками (`MAX_LEG_KM`). Обратная сторона того же
  каталога: в сгенерированном городе места лежат внутри всего прямоугольника города, и в Сочи запрос на
  два часа дважды возвращал две точки в 4,1 км друг от друга — час из 120 минут уходил на дорогу. Правило
  проверяется по соседним остановкам, а не по крайним: цепочка из восьми коротких шагов имеет право
  пересечь город, а один длинный прыжок — это уже не прогулка, а переезд. Точка старта под правило не
  попадает: откуда гость начинает — его выбор, а не обещание планировщика.
- `/routes/generate` принимает необязательную пару `start_lat` + `start_lon` — откуда гость собирается
  начать прогулку. Без неё маршрут строится как раньше, с первой точкой по выбору планировщика и нулевым
  переходом к ней. С ней первый отрезок становится расходом: `travel_minutes_from_prev` и
  `distance_m_from_prev` у первой остановки считаются от старта и съедают бюджет времени, а до мест, до
  которых не дойти за отпущенное время, дело вообще не доходит — поэтому слишком далёкий старт даёт тот
  же `404`, что и пустая категория. Ответ всегда содержит `start`: `null`, если старта не было, иначе
  переданные координаты — сохранённый маршрут возвращает их вместе с полезной нагрузкой. Половина пары
  (только широта) — `422`: одна координата точку не задаёт. Стартовая точка **не** участвует в правиле
  150 метров и в разбросе: встать у двери того самого объекта, куда тебя и просили привести, — это смысл
  старта, а не дубль остановки. Совпадает же с точкой старта **место из каталога** — то есть гость стоит
  прямо у его двери, — оно из кандидатов выпадает: идти 0 метров до того, где ты уже и так находишься,
  нечего. Экран настройки предлагает стартовать адресами из этого же каталога, поэтому без этого правила
  прогулка возвращала гостя на точку, с которой он только что вышел (10 объектов из 43 на четырёх часах).
- Неизвестное поле в теле запроса — `422` со списком ошибок, а не молчаливое игнорирование: проглоченный
  `budget` неотличим от проигнорированного лимита.
- `q` ищет подстрокой по `title`, `description`, `address` и `category`: регистр, пунктуация и лишние
  пробелы не важны, но найтись должны **все** слова запроса. Пустой по словам запрос (`?`, `«»`) не находит
  ничего.
- `radius_km` — прямое расстояние от `near_lat`/`near_lon`, а не время в пути; задаётся только вместе с
  обеими координатами, иначе `422`.
- Итоги пагинации у `/places` лежат в заголовках: `X-Total-Count` — размер выборки до `limit`, `X-Offset` —
  сдвиг ответа. Тело остаётся голым массивом, конверт `{items, total}` не вводится. Для кросс-origins
  запроса этого мало: браузер не отдаст JS заголовок вне CORS-safelisted списка, поэтому `configure_cors`
  прописывает оба имени в `Access-Control-Expose-Headers`, а `tests/test_cors.py` это проверяет.
- `GET /cities` — готовый источник для селектора города: список `[{city, place_count, categories}]` в порядке
  появления городов в каталоге.
- `GET /chips` — так же честно рисует ряд «Чем хочешь заняться?»: `[{id, label, emoji, tags, place_count}]`
  в постоянном порядке (кофе, культура, прогулка, перекус, фото). Чипа с нулём мест в ответе не бывает —
  `place_count` ограничен `ge=1` на уровне контракта, а пустой чип просто не попадает в список. Поэтому
  свой список «что из этого вообще работает» фронтенду держать негде: экран рисует то, что пришло.
- У места две независимые оси: `category` (что это такое) и `tags` (зачем сюда идут). `POST /routes/generate`
  принимает `tags: [str]` рядом с `categories`; внутри списка — **ИЛИ**, между осями — **И**, пустой список не
  фильтрует вовсе. Один чип отправляет `tags: [chip.id]`, их `id` и есть теги. Неизвестный тег даёт `404`,
  как неизвестная категория, а не `422`: для клиента это «под фильтр ничего не подошло».
- Тот же тег есть у витрины: `GET /places?tag=food&tag=coffee`. Предикат один на три экрана — счётчик
  в `place_count`, фильтр генератора и этот список, — поэтому «☕ 5» на чипе и пять карточек в листе
  обязаны сходиться, и `tests/test_places_api.py` сверяет ровно это. Отличается только цена промаха: пустая
  выборка здесь — `200 []` (полка пуста, полка существует), как и у неизвестной `category`, а не `404`.
  Значение `tag` — строка, не `TagId`: неизвестный тег не должен превращаться в `422` рядом с категорией,
  которая отвечает `200 []`.
- `image_url` заполнен руками у 32 объектов из 43: это прямые ссылки на `*.wikimedia.org`, в основном
  миниатюры Commons, а для трёх файлов — оригиналы, когда уменьшать нечего. Commons отдаёт их только
  описательному `User-Agent`, поэтому они подобраны не запросом из приложения, а заранее и
  лежат в `data/places.json`. Одиннадцать `null` — осознанные: у «Парка Собино» фото самого парка на
  Commons нет, а кладбищенский памятник вместо витрины не показатель, и десять кофеен из OSM никто не
  снимал на свободную лицензию — ссылка на чужой снимок вместо вывески была бы враньём. Ни сервер, ни
  приложение в Wikimedia не ходят: клиент только грузит картинку. Лицензии — CC, атрибуция в интерфейсе
  пока не показана.
- У новых записей каталога есть ключ `provenance` (`source_url`, `last_verified`, `unverified_fields`).
  Он ничего не меняет в ответе API — `Place` объявлен как `extra="ignore"` и выбрасывает его, — это следы
  для редактора данных: координаты берутся из реестра, а не из головы, а цена, часы и рейтинг, которые не
  удалось сверить с первоисточником, честно перечислены в `unverified_fields` вместо того, чтобы выглядеть
  проверенными. Реестров два. Викиданные — для достопримечательностей: у них есть утверждения с
  координатами, которые кто-то уже проверял. OpenStreetMap — для обычных адресных мест (кофейни,
  фастфуд, уличные скульптуры), потому что ни одной кофейни Ростова на Викиданных нет вовсе, а чип
  «Взять кофе» обязан вести к реальным дверям: в `source_url` тогда ссылка на узел или способ OSM.
  Данные OSM распространяются под лицензией **ODbL 1.0** с атрибуцией «© участники OpenStreetMap» —
  на экране, где показан маршрут, её стоит упомянуть рядом с атрибуцией Wikimedia.
- Справка по месту — это два эндпоинта, а не четыре поля у `Place`: `GET /guides` (указатель: какие
  справки уже написаны — плашку «📖» вешают на этот список, а не проверяют `404` на каждом месте) и
  `GET /places/{place_id}/guide` (экран чтения). Справок пока 8 из 43 мест; у остальных `404` с текстом
  «ещё нет» — это не ошибка, а очередь.
- Текст справочного экрана живёт в `data/place_guides.json` и целиком проверяется при загрузке: `history` —
  2–3 абзаца, `highlights` — 3–5 коротких фактов, каждый снимок обязан лежать на
  `https://*.wikimedia.org` и нести `credit` с `license` (у `public domain` страницы лицензии нет), а
  `provenance` — ссылку на статью и дату сверки. Пустой `media` без `media_note` файл не принимается:
  отсутствие фото должно быть решением, а не недосмотром.
- `title`, `category`, `city`, `location`, `price`, `working_hours` и `visit_duration_minutes` в ответе
  справки — эхо каталога, а не поля редакторского файла: цена билета не может разойтись с карточкой
  места, потому что её там просто нет.
- `nearby` (4 ближайших объекта, по прямой) считает тот же пешеходный шаг, что и
  `travel_minutes_from_prev` в маршруте, — «5 минут» на экране справки и в маршруте это одно число, а не
  два предположения.
- Сохранённый маршрут — это дословный ответ генератора, но обёртка `route` есть только в **ответе**.
  В **запросе** `POST /routes` тело развёрнуто верхним уровнем: те же ключи, что вернул
  `POST /routes/generate`, плюс необязательный целый `user_id` (`SaveRouteRequest` наследуется от
  `RouteResponse`); `extra="forbid"` отвергнет присланную обёртку `route` ровно так же, как и любой
  другой посторонний ключ. Наружный `route_id` выдаёт база — целое число, по нему и обращаются;
  вложенный `route.route_id` — тот самый одноразовый uuid4, `GET /routes/{uuid}` даёт `422`.
  Запись переживает перезапуск процесса — в этом весь смысл эндпоинта.
- `user_id` у сохранённых маршрутов **не аутентифицируется**: у HTTP-API нет ни сессии, ни токена, ни куки.
  Фильтр `?user_id=` — удобство для своего списка, а не граница доступа: без него видно чужие записи, а
  чтение по `route_id` владельца не проверяет вовсе. Настоящий контроль появится только вместе с
  аутентификацией поверх этих эндпоинтов.
- `503` означает, что файл каталога недоступен или повреждён, — а на эндпоинтах сохранённых маршрутов ещё
  и что база не отвечает. Справочные эндпоинты падают в `503` по своему файлу (`data/place_guides.json`
  битый, отсутствует, или справка ссылается на место, которого в каталоге уже нет); при этом `/places`
  и генератор маршрутов продолжают работать — в `detail` назван тот файл, который не читается.
- `/health` отвечает `200` и при недоступной базе — на него висит `HEALTHCHECK` контейнера, и валить бота
  из-за короткого сбоя SQLite не нужно. Проверяют готовность отдельно: `/readyz` отдаёт `503`.

## Аналитика пилота: события и метрики §8

Продуктовая проработка обещает семь чисел после двух недель пилота («время до маршрута», две конверсии,
завершение, соответствие времени, полезность, стабильность). Почитывать их было неоткуда, поэтому бот
складывает события в таблицу `analytics_events`, а `GET /api/v1/metrics/funnel` отдаёт ту же таблицу
обратно — строка в строку, с формулировкой каждой метрики и её же знаменателем.

```bash
curl -X POST http://127.0.0.1:8080/api/v1/events -H "Content-Type: application/json" \
     -d '{"name":"miniapp_open","session_id":"pilot-0001"}'
curl "http://127.0.0.1:8080/api/v1/metrics/funnel?days=14"
```

- Семь имён взяты из §8 дословно: `miniapp_open`, `route_setup_started`, `route_generated`,
  `route_started`, `poi_opened`, `route_completed`, `route_rated`. Восьмое — `client_error` — в списке
  продукта отсутствует, хотя метрика «техническая стабильность ≥ 95 %» в той же таблице есть: без него
  эту строку считать не из чего. Это вопрос продукт-менеджеру, а не тихое расширение контракта.
- **Время ставит сервер, а не клиент.** Воронка измеряет интервалы *между* событиями одной сессии, и
  часы устройства-отправителя превратили бы «время до готового маршрута» в погрешность этих часов.
  Обратная сторона: события нужно отправлять по мере того, как они происходят, — пакет вчерашних событий,
  отправленный ночью, покажет мгновенную воронку.
- **Каждая доля считается по сессиям, а не по строкам.** `session_id` выдаёт клиент (uuid4), и
  повторный `route_started` после ретрая не удваивает конверсию. `session_id` ограничен формой
  `[A-Za-z0-9_-]{8,64}`: идентификатор «1», общий у всех, превратил бы семь метрик в одну.
- У события есть поля, которые читает только своё событие, и обязательные для него. `rating` при
  `miniapp_open` отвергается, а не игнорируется: иначе он молча попадёт в «полезность». `route_rated`
  без оценки и `route_completed` без парой `requested_minutes`/`actual_minutes` — `422`: такое событие
  не считает ничего, и собрать его «на всякий случай» хуже, чем не собрать.
- `route_completed` приносит и заказанное, и фактическое время — метрика «±15 %» иначе осталась бы
  пожеланием. `poi_opened` обязан нести `place_id`, иначе непонятно, какой экран вообще работал.
- Нет наблюдений — `null`, а не `0`. «Никто не начал прогулку» и «все начали и никто не завершил» —
  разные новости для разных людей, и дашборд, подкрасивший первую красным, отправит чинить не то.
- `time_to_route` — медиана, а не среднее: один гость, который открыл приложение, ушёл за кофе и
  вернулся через час, на троих гостей по 12 секунд сдвинул бы городскую метрику с 0,2 мин до 20,1 и
  уронил бы пилот мимо цели.
- `user_id` и `session_id` **не аутентифицируются** — то же самое, что у сохранённых маршрутов: у HTTP-API
  нет ни сессии, ни токена, ни куки. Кто угодно может наотправлять оценок «5», и это двигает «полезность».
  Для закрытого пилота на 30–50 приглашенных это приемлемо; цитировать эти числа наружу можно только
  после того, как поверх эндпоинтов появится аутентификация.
- Мини-приложение пока **не отправляет ни одного события** — эндпоинт готов, клиента нет. Экран
  прохождения маршрута есть («Начать прогулку» → «Я на месте» → «Завершить прогулку» с итогом
  «пройдено/затрачено против плана»), но итог считается на клиенте и в `POST /api/v1/events` не
  пишется, а экрана оценки нет вовсе — поэтому `route_completed` и `route_rated` сейчас неоткуда ждать,
  и две метрики пилота остаются `null`, пока фронтенд не начнёт отправлять события.

## Шпаргалка: деплой на сервер одной командой

```bash
git clone <repo> && cd hackaton_max \
 && cp .env.example .env && nano .env \
 && docker compose up --build -d && docker compose logs -f bot
```

Дальше — HTTPS на 443 (MAX не принимает http-вебхуки и сам порт 8080), например через Caddy:

```bash
docker run -d --name caddy -p 443:443 -v $PWD/Caddyfile:/etc/caddy/Caddyfile -v caddy_data:/data caddy
```

после чего включить авто-подписку и проверить:

```bash
docker compose exec bot python main.py --mode=setup-webhook   # подписка + меню команд
curl https://your-domain.com/health
```

Полезно знать: MAX **копит** подписки (не заменяет) и **отписывается через 8 часов** без успешного
ответа. `--mode=setup-webhook` и старт вебхук-режима сами чистят устаревшие URL перед подпиской.
Локальная база живёт в `./data/bot.db` и переживает пересборку образа.

## Известные ограничения

Данные.

- **В репозитории один город** — Ростов-на-Дону, 90 мест (43 вручную сверенных + 47 собранных
  автокаталогом). Казань и Сочи собраны тем же пайплайном и стоят на бою, но как эксперимент в git не
  лежат: локальный стенд после клона показывает один город, и это ожидаемо.
- **Часть полей места не сверена с первоисточником**: цена, часы работы, «Пушкинская карта» и
  длительность визита перечислены в `provenance.unverified_fields` — ровно для тех мест, где их негде
  было взять. Рейтинг в автокаталоге — вообще не оценки посетителей, а «сколько мира написало об этом
  месте» (статья в Вики, элемент Викиданных, фото, `tourism=attraction`); в `provenance.rating_basis`
  это названо `attestation`.
- **Длительность остановки придумана в коде**: в OSM этого поля нет, поэтому Музей 45 мин, Театр 90,
  Галерея 45, Парк 60, Памятник 20, Архитектура 20, Кафе 30. Это время прогулки, а не экспозиции.
- **Справок 8 на 90 мест**: остальные точки открываются с честным «ещё нет», это очередь, а не ошибка.
- **Атрибуция не показана**: фотографии — CC с Wikimedia, координаты — ODbL с OpenStreetMap; требовать
  указывать автора обязывает лицензия, а интерфейса атрибуции пока нет.

Маршруты.

- **Минуты — модель планировщика, а не ETA навигатора**: 4,8 км/ч плюс три минуты на выход из здания.
  От OSRM берётся только длина перехода: пешеходный ETA публичного инстанса на 809 метров отдаёт
  107 секунд (27 км/ч), и обещать посетителю такое время нельзя.
- **Без ответа OSRM линия становится хордой** между маркерами; это помечено в ответе
  (`geometry_source: "straight_line"`, `walk_distance_m_from_prev: null`) и нарисовано пунктиром,
  но путь по тротуарам в этом случае не измерен.
- Планировщик тратит **85 % заказанного времени**, остаток — резерв на очереди и закрытые двери;
  экран обязан показывать запас, а не прятать его.

Интерфейс и контур.

- **Аутентификации нет**: ни сессии, ни токена, ни куки. `user_id` и `session_id` не проверяются,
  поэтому список сохранённых маршрутов и метрики пилота — удобство для закрытого пилота, а не граница
  доступа; цитировать эти числа наружу можно только после появления аутентификации.
- **Фронтенд не отправляет событий аналитики**, экрана оценки маршрута нет, тёмной темы нет, тестов
  фронтенда нет, а иконка перестановки точек (⇄) пока декоративная.
- **`open_app` в MAX требует привязки Mini App в кабинете**: непривязанный URL роняет всё сообщение с
  `404 Link not found`; без привязки кнопка откатывается на `link` с диплинком (см. раздел про
  регистрацию ссылок).
- **Вебхуку нужен валидный HTTPS-сертификат от доверенного ЦС** (с 25 мая 2026 MAX не принимает
  http-вебхуки и самоподписанные), поэтому демо в мессенджере — единственный шаг, который локальным
  Docker не закрывается.
- Открытые источники (Overpass, Nominatim, OSRM, Commons) anonymous и лимитированы: 429/504 — норма,
  поэтому у автокаталога есть пауза между запросами, ретраи и зеркало, а у генератора маршрута —
  короткий таймаут с честным откатом.

## Остановка и повторный запуск

```bash
docker compose stop          # пауза: контейнеры остановлены, образы и данные целы
docker compose start         # то же самое снова, за секунды
docker compose down          # удалить контейнеры и сеть; data/ на хосте остаётся
docker compose up -d         # обычный фоновый запуск
docker compose up --build -d # пересобрать образы после изменения кода
docker compose ps            # что живёт и healthy ли бэкенд
docker compose logs -f bot   # логи API; miniapp — тем же вызовом с другим именем
docker compose restart bot   # перезапуск одного сервиса (проверка шага 10 сценария)
```

Ничего из пользовательских данных при остановке не теряется: сохранённые маршруты и события лежат в
именованном томе `bot-state`, каталог мест и справки — в файлах `data/` этой папки. `docker compose
down` убирает контейнеры и сеть, но том остаётся; `down -v` — единственный способ его удалить.

Сброс к чистому состоянию, если тестовые данные помешали проверке:

```bash
docker compose down -v     # контейнеры, сеть и том с базой удалены; каталог в data/ остался целым
docker compose up -d       # том создан заново: init_db поднимает пустые таблицы users, saved_routes
```

Что произойдёт при повторном `up`: образы берутся из кэша, база поднимается в чистом томе (`init_db`
при старте), каталог перечитывается с диска — в логе видно `Loaded 90 places from 2 file(s)`.
